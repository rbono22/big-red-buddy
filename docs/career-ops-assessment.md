# Career Ops integration assessment

Reviewed 2026-11-10, public source commit [`605a1e61ee2b0d269b371ebe4351180993ebbfee`](https://github.com/career-ops-hq/career-ops/tree/605a1e61ee2b0d269b371ebe4351180993ebbfee). Source inspection only: nothing was installed or executed, and no student data was sent to this repository or its services.

**Recommendation:** reuse selected ideas or audited modules behind BRB's existing student-scoped APIs. Running the entire CLI with a shared profile directory would not provide the isolation required for a student service.

The exact boundary matters: the preparation script says “Never POSTs anything”; the live mode says “Do not submit the form.” The project's disclaimer also acknowledges that prompt compliance cannot guarantee agent behavior. These are not claims that applications have been submitted or that arbitrary ATS forms work reliably. Sources above document intended behavior; no runtime effectiveness was measured here.

For BRB, adapt the profile schema into encrypted tenant records with explicit student declarations, replace filesystem CV/report access with the scoped store, and run bounded extraction/drafting through the existing queue. Retain evidence links, require review before answers become reusable, and leave missing facts blank. Telegram should authenticate through the existing chat binding and expose upload, review, list, draft and manual-answer commands; it must never choose a tenant from message text.

BRB's current Telegram implementation prepares materials and stores reviewed answers. It has no employer submission, browser-session or ATS-credential tool. A future form assistant would require separately isolated per-student browser sessions, permitted source adapters, exact posting verification, explicit field review and submission confirmation, plus site-specific tests. That work is a separate integration; adding Career Ops alone does not implement it. No upstream source was copied into BRB by this assessment.
